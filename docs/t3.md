# T3 and Team MCP

Kinmesh talks to the outside world through two narrow interfaces: the **T3 adapter**, which runs agents on independently installed, unmodified T3 Code, and **Team MCP**, which lets those agents act in Kinmesh. Neither embeds the other. Kinmesh never imports T3 code or uses T3's private packages, databases or WebSockets, and the product never shells out to T3's CLI; `npm run architecture` guards this statically. Running the gates that exercise both against real T3 is in [operations](operations.md#live-and-native-gates).

## T3 adapter

`src/domain/execution.ts` owns `ExecutionBackend`: project or scratch targets, operation intent, stable environment/thread/run references, normalized observations and discriminated dispatch, wait and stop results. `src/adapters/t3` implements it with the official MCP SDK (Streamable HTTP and OAuth), Zod and Ajv. There is no unauthenticated execution API; the [Inbox](collaboration.md#agent-inbox) is the only caller in the product.

### Supported T3

Kinmesh supports **T3 0.1.5 or newer**. The environment descriptor must report a plain `major.minor.patch` version at or above that floor, and every tool call is validated against the JSON schemas T3 advertises; a missing tool or schema fails closed as `incompatible`, and a reply outside those schemas or the contract Kinmesh reads it by as `unreadable`. That contract takes what the schemas allow: a field T3 may leave out or send as null (a provider's `runtimeModes`, a thread's `link`) is read as absent. Asking again returns the same reply, so neither is retried as an outage. Each newer stable release is proposed with a check that it serves every tool a run uses as Kinmesh reads it ([newer T3](operations.md#newer-t3)); adopting one with a changed MCP contract means reviewing its schemas and running the [native gates](operations.md#live-and-native-gates) against it; fix the adapter, never T3. `npm run t3:smoke` takes a person's sign-in (`KINMESH_T3_AUTH_FILE`) or a session T3 issued (`KINMESH_T3_CREDENTIAL_FILE`); with `orchestration:operate` it also checks every tool a run uses.

What Kinmesh relies on from T3 (observed on 0.1.9):

- **Sign-in.** T3's authorization server offers only the authorization-code grant, to public clients with S256 PKCE, and issues no refresh token. An access token lasts 30 days, which its token response states as `expires_in`; then a person signs in again.
- **Authority.** The grant's runtime-mode ceiling is the mode the person approves: `approval-required` for Supervised, `auto` for Auto, `full-access` for Full access; a broader mode is refused (`runtime_mode_escalation_denied`). Full access also grants `settings:write` and `source-control:write`, which changing projects or environment settings, `t3_project_create` included, needs; without them it is refused with `capability_denied`. Only that OAuth approval sets a ceiling above `approval-required`: a session from `t3 auth session issue` has `approval-required` whatever its scopes, and nothing in T3's CLI, settings or managed policy raises it (a policy's `maxRuntimeMode` only lowers every ceiling).
- **Runtime modes.** `orchestrator_capabilities` reports the grant's ceiling as `runtimeMode` and, per provider, the modes it runs as `runtimeModes`; a provider need not run every mode (pi runs `approval-required`, `auto-accept-edits` and `full-access`, not `auto`).
- **Projects.** `t3_project_create` needs a Full access grant, which a session from `t3 auth session issue` never is: it acts at most in `approval-required`, whatever its scopes. `t3 project add <path>` on the T3 machine registers a folder as a project and refuses one already registered. A thread launched with a project ID and `workspaceStrategy: root` runs in that folder under a Supervised grant. The hub only finds projects; Kinmesh's [space provisioner](operations.md#the-space), beside T3, makes them.
- **Sessions.** T3's MCP endpoint is stateful: `initialize` returns an `Mcp-Session-Id`, and a request without it is refused (400). A proxy in front of T3 passes that header through.
- **Steering.** A message sent in `auto` mode to a run waiting for an approval steers that run, and the agent sees it once the approval is answered. If the run is interrupted instead, the steered message ends with it; nothing starts a new turn. A send's reply says how T3 took it (`started`, `queued`, `steered`), which is how the Inbox knows to send a lost message again.
- **Interrupting.** `t3_thread_interrupt` answers `interrupt_requested`, and the run, waiting for an approval or not, is `interrupted` a moment later. Messages queued behind it then run in turn. With `stop: true` (what T3's own Stop does) the queue is held instead, until the thread's next turn starts; Kinmesh never sends it, so the agent's later messages are not held back.
- **Waiting for an approval.** A run waiting for an approval still reads `running`; what waits is its approval, an `activity` item of that run with status `waiting` (type `approval_request`, its text the command or change asked about). `t3_pending_request` answers questions only, never an approval, so approving happens in T3. A thread's `pendingRequestCount` counts every such item, including the one a run interrupted while waiting leaves behind for good, so the adapter takes a run's pending requests from its own items, read from the thread's latest activity only while the thread has any.

### Endpoints

Use the exact canonical `https://host/mcp` URL from T3 **Settings → Environments → environment menu → Copy MCP URL**, without userinfo, query or fragment. Plain HTTP is allowed only on loopback. The endpoint must be reachable from both the machine that holds the credential and the owner's browser: a host-local `http://127.0.0.1:3773/mcp` produces an authorization page on the browser computer's own loopback. Never rewrite an issued authorization URL to work around this.

### Preflight

```sh
KINMESH_T3_ENDPOINT=https://your-t3.example/mcp npm run --silent t3:preflight
```

Preflight reads only `KINMESH_T3_ENDPOINT` and needs no credential. Under one 10-second deadline it checks that unauthenticated `/mcp` answers 401 with a Bearer challenge, that the public environment descriptor names an environment on a supported version, and that the pinned OAuth metadata offers S256 PKCE, issuer in the authorization response, the authorization-code grant for public clients, and the `orchestration:read` and `orchestration:operate` scopes. Discovery is same-origin, GET-only, refuses redirects, bounds JSON to 64 KiB and sends no cookies or authorization. Output is fixed PASS/FAIL text. Preflight never registers a client, opens consent, calls a tool or runs a model.

### T3 sign-in

Kinmesh holds its **own** T3 OAuth grant; provider logins, Team MCP credentials and T3's native pairing are separate. A person of the team approves, on T3's consent page, how agents run: **Supervised**, where T3 asks a person for every action that needs approval; **Auto**, where T3 lets through what it judges safe; **Full access**, where nothing waits for approval, only for a T3 that runs isolated ([security](security.md#t3-credentials)); or **Read only** for inspection. Agents' runs launch in the chosen mode ([operations](#operations)). The hub reads that choice from T3 once, at sign-in, and the workspace names the mode runs use beside the T3. T3 may ask for a pairing code from **Settings → Sharing & access**; it must come from the environment serving the chosen endpoint. Where the deployment runs Kinmesh's [space provisioner](operations.md#the-space) beside T3, a person gets one in 连接 › T3 (**生成配对码**, `POST /api/teams/:teamId/t3/pair`, 409 without a provisioner): the code, when it stops working (five minutes), and `<T3 origin>/pair#token=<code>`, which pairs the browser that opens it. Revoke or rotate grants there too.

**From the workspace.** The agent page connects T3 once per team (UI in [DESIGN.md](design/DESIGN.md#components)). With a loopback origin the hub probes only the fixed loopback address `127.0.0.1:3773` for a local T3 desktop and accepts it only if it returns a valid environment descriptor; otherwise the owner pastes the MCP URL. The approval URL goes only to the owner's browser.

With an HTTPS origin the owner's browser is on another computer, so the hub probes nothing and takes only an HTTPS MCP URL, one that both the hub and the owner's browser reach, since T3's approval page is on that origin. After approving, T3 sends the browser to the loopback callback, which loads nothing there; the owner pastes the full address from the address bar into the panel. The hub accepts it by the terminal's manual-mode rules (below): the exact callback scheme, host, port and path, one each of `state`, `code` and `iss` matching this sign-in, and only once. The hub keeps listening on its own loopback callback too; the first valid callback wins. This sign-in has ten minutes, since the owner may first pair their browser with T3; T3's authorization code still lasts about a minute after approving, so paste it at once. The resulting credential is stored as described in [security](security.md#hub-held-worker-secrets) and is replaced only when the owner asks. One sign-in runs at a time, because the callback port is fixed.

| Route (a person's session only)                      | Purpose                                                                                                                                                                                                                                                  |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/teams/:teamId/t3`                          | Connection and, for the credential runs use (below), its access (`operate`, `read` or none) and mode; whether none is honoured; sign-in state; to whoever started a sign-in under way, its approval page (`authorizationUrl`), so a reload can finish it |
| `GET /api/teams/:teamId/t3/local`                    | The local T3 endpoint, if one answers (never with an HTTPS origin)                                                                                                                                                                                       |
| `POST /api/teams/:teamId/t3/connect`                 | `{endpoint,replace}`; starts sign-in, returns the approval URL; 409 for any T3 but the one the deployment connects, when it does                                                                                                                         |
| `POST /api/teams/:teamId/t3/callback`                | `{url}`; the approval's callback, pasted by the owner (HTTPS origin); 204, or 400 for any other address                                                                                                                                                  |
| `GET /api/teams/:teamId/t3/providers`                | Providers and models the connected T3 can run; 503 after 3 s without T3                                                                                                                                                                                  |
| `POST /api/teams/:teamId/agents/:agentId/connect`    | `{providerId,modelId}`; sets what the agent runs on in the connected T3 environment; issues the worker credential if it has none, starts the worker                                                                                                      |
| `POST /api/teams/:teamId/agents/:agentId/disconnect` | Revokes the worker credential and removes its file                                                                                                                                                                                                       |

**When a sign-in ends.** The credential keeps when T3 stops honouring it: `expires_in` counted from just before the token was asked for, so it never ends later than T3's own clock says. A credential T3 gave no lifetime for is not known to end; one T3 refuses while the hub holds another it honours (the deployment's session, below) was revoked, and ends then. From seven days before a person's sign-in ends, the workspace snapshot's `attention.t3` names the T3, its end and the mode runs fall back to once it has ended (the deployment's session, or none) for every person of the team, and the workspace offers to reconnect T3 there ([DESIGN.md](design/DESIGN.md#components)); reconnecting is the same sign-in as connecting, to the connected endpoint, replacing the credential only once T3 approves. Once the end has passed, the worker sends nothing to T3 under it. With the deployment's session honoured, runs use that instead and nothing waits. Otherwise each delivery the worker claims waits `ready` with the reason `sign-in-expired` and goes on after the next sign-in, which is the same authority (below) when it is the same endpoint, environment and scopes.

**From the deployment.** When the hub runs beside T3 (one cluster), the deployment can connect them, so agents run without anyone signing in; its runs launch Supervised (below). T3 issues the hub a session with exactly the scopes it should hold: `t3 auth session issue --scope orchestration:read --scope orchestration:operate --ttl 30d --label kinmesh-hub --subject mcp-client --json` (T3's MCP endpoint takes only a session whose subject is `mcp-client`), adding `settings:write` and `source-control:write` for Full access. Its ceiling is `approval-required`, so its runs launch Supervised. The deployment keeps that output, renewed before it expires, in the file `KINMESH_T3_CREDENTIAL_FILE` names, and sets `KINMESH_T3_ENDPOINT`. On start and every minute the hub reads the file; when it changed, it asks T3's environment descriptor which environment it is and T3 the session's ceiling, stores the session where its worker reads it, apart from any person's sign-in ([security](security.md#hub-held-worker-secrets)), and records the team's connection. The session's `expiresAt` is kept as its end; nobody is asked to renew it, and once it has passed without a person's sign-in, deliveries wait with `sign-in-expired` until the deployment's renewed session arrives. A renewed session for the same endpoint, environment and scopes is the same authority (below), so runs under way still publish and conversations keep their threads. When the deployment stops connecting the hub (it no longer sets `KINMESH_T3_ENDPOINT`), the hub ends the session the deployment issued when it starts: runs use a person's sign-in, or deliveries wait with `sign-in-expired` and the workspace asks a person to sign in, as for any sign-in that ended.

**Both at once.** A person of the team may still sign in, to the T3 the deployment connects (any other answers 409), choosing a broader mode such as Full access; the workspace offers it as **Reconnect**. The hub keeps both, and agents' runs use the credential T3 still honours that lets them go furthest (by its ceiling; one that only reads goes nowhere), the person's when the two are equal. So a person's Full access sign-in is used while it lasts, and when it ends or T3 refuses it the hub uses the deployment's session at once, while everyone is invited to sign in again. Each delivery chooses when the worker claims it: a delivery already frozen keeps the credential it was frozen under while T3 honours it, so a run under way finishes and posts under the authority it launched with. One whose credential has ended can't be posted under another authority: if it may have reached T3 it stops as `authority-changed` and a person asks again; if it provably never did, it is frozen again under the credential runs use now. The two credentials are two T3 authorities when their scopes differ (Full access adds scopes), and a thread keeps its mode, so a conversation's next message after a switch starts a new thread ([operations](#operations)).

**From a terminal**, for a worker the operator runs:

```sh
KINMESH_T3_ENDPOINT=https://your-t3.example/mcp \
KINMESH_T3_AUTH_FILE=/private/kinmesh/t3-oauth.json npm run t3:auth
```

The default `browser` mode listens on `http://127.0.0.1:49871/callback` and opens the approval page without printing its URL. With no local browser, set `KINMESH_T3_AUTH_MODE=manual` in the owner's private interactive terminal on the target machine (never through an agent tool, CI, a recorder or redirected output). Manual mode refuses non-TTY use and writes the one-time URL only to `/dev/tty`. Open it in a browser, approve, then paste the **complete final address-bar URL** (the browser's failed load of `127.0.0.1:49871` is expected) into the hidden prompt. Authorization codes expire within about a minute; the whole flow has a three-minute deadline. Failed attempts are not retried; start again.

Both modes accept exactly one `state`, `code` and `iss` on the exact callback, matching the random state and pinned issuer, and reject everything else. The SDK owns discovery, dynamic registration, S256 PKCE and exchange. The CLI refuses any existing destination file and writes a new 0600 file atomically; it prints no token, registration secret or verifier.

### Smoke check

```sh
KINMESH_T3_ENDPOINT=https://your-t3.example/mcp \
KINMESH_T3_AUTH_FILE=/private/kinmesh/t3-oauth.json npm run t3:smoke
```

The smoke check initializes MCP, lists tools, and calls only `t3_environment_read` and `orchestrator_capabilities`. It validates the environment, version and schemas, and reports whether the grant includes `orchestration:operate` and its capability ceiling. It never launches a thread, runs a model or writes the journal. A Read only grant passes but cannot run agents.

Credential files follow the [T3 credential rules](security.md#t3-credentials). Expired or revoked grants need a new T3 sign-in.

### Operations

| Domain operation | T3 tool and semantics                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Connect          | `t3_environment_read`, `orchestrator_capabilities`, `tools/list`; pins environment identity and version                                          |
| Project          | `t3_project_list`, paged: the project whose `workspaceRoot` is a channel's folder; only with a [space](operations.md#the-space)                  |
| Launch           | `t3_thread_launch`: project ID at its `root` **or** `scratch: true`, advertised provider/model, explicit runtime mode (below), `clientRequestId` |
| Read             | `t3_thread_read`: thread, `recentRuns`, bounded message pages with explicit truncation                                                           |
| Follow-up        | `t3_thread_send` with a persisted key: `auto` for the Inbox's next message in a conversation, `queue` for one sent again; never `restart`        |
| Wait             | `t3_thread_wait`, 1–20000 ms; `timedOut` is not completion; followed by an authoritative read                                                    |
| Stop             | `t3_thread_interrupt` for the run, without `stop`; acknowledgement is not terminal; a read decides                                               |
| Reconcile        | Stored reference → read; otherwise replay the same persisted command and key, then read                                                          |

A launch runs in the grant's ceiling, the mode the person chose: `full-access`, `auto` or `approval-required`. When the provider doesn't run that mode, it runs in the broadest mode below it that the provider runs (pi under Auto runs `auto-accept-edits`); never above the ceiling. Only providers that run a mode at or below the ceiling are offered. The mode is frozen with the delivery, and a thread keeps the mode it was launched in, so a conversation whose thread runs in another mode than a launch would now use starts a new thread. `npm run t3:smoke` reports the ceiling and the mode each provider's runs launch in.

A read selects the requested run from `recentRuns`; a run outside T3's latest 50 is `unobserved`, never another run's status. `completed` maps to `succeeded`; `interrupted`, `cancelled` and `rolled_back` to `stopped`; `waiting` stays nonterminal. Acceptance is always `not-evaluated`. Live harnesses also call `t3_thread_organize` to archive their own threads.

### Durable operations and recovery

The `execution_operations` table records, per endpoint/environment scope, actor and caller `operationKey`: the input and authority fingerprints (hashes, not tokens; the authority is the T3 endpoint, environment and granted scopes, so a renewed token for the same is the same authority), a random stable native request ID, tool and payload, phase and any reference. Intent is persisted **before** dispatch. A claim takes a generation, random token and 120-second lease in one SQL compare-and-set; every journal write checks them against database time, so an expired or superseded owner cannot overwrite a newer outcome. There is no heartbeat; a crashed process's lease simply expires.

| Phase / outcome                                                        | Safe next action                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `prepared`                                                             | Claim and dispatch the persisted request ID                               |
| `dispatching`, crash, lost reply, timeout, cancellation in flight      | Return `uncertain` with the operation ID; reconcile, never mint a new key |
| Valid reply, read fails                                                | Keep the provisional reference; reconcile by read only                    |
| Reply that is `unreadable` or `incompatible`                           | Return `uncertain` with that reason; reconcile only when a person retries |
| Valid reply, matching run/thread                                       | Mark `known`; duplicates get the stored reference                         |
| Native `capability_denied` or HTTP auth rejection before a valid reply | Persist the rejection and fail; generic errors are not denial             |
| Native `thread_not_found`                                              | Persist the rejection and fail: the thread is gone                        |
| Unsupported version or missing `clientRequestId`                       | Fail before mutation                                                      |
| Different authority fingerprint                                        | Conflict; a person resolves the existing intent                           |

Same key with different input is a conflict, unless T3 refused the first with `thread_not_found`: nothing was done, so the key may carry another operation. SDK requests time out after 30 seconds and each attempt has a 60-second deadline, inside the lease. T3's own idempotency on the request ID is the cross-system deduplication; the lease only serializes Kinmesh. An aborted wait does not stop T3 work; use an explicit stop. Keep the host clock synchronized. The journal may contain prompts; protect it as team data.

### Checking a run

Anyone of the team can ask T3 for the live state of a recorded run (**在 T3 中查看** on the agent page). It reads through the team's T3 connection — the one approved with **连接 T3** — so there is nothing else to configure; before a team connects T3, checking isn't offered. The check uses only read tools (`orchestration:read` is enough), never operating tools, and never acquires or renews tokens.

`GET /api/teams/:teamId/agents/:agentId/executions/:executionId/native` requires a person's session. The server loads the exact stored association before reading any credential; nothing in the request chooses the endpoint, credential, environment or thread. It calls only `t3_environment_read` and `t3_thread_read` under an eight-second deadline, refuses redirects, rechecks the person's access after the read and never stores the result. Any native failure is the same generic 503. The result is a timestamped read of the run's exact status; pending requests are thread-scoped.

An **Open in T3** link opens the run's thread in the web UI of the T3 that served the read, on its endpoint's origin: `<origin>/<environment>/<thread>`, each ID one URL-encoded path segment (`https://t3.example/<environment>/mcp%3Alaunch%3A…`). The server builds it from the run's exact environment and thread after T3 has read them; the `thread.link` T3 returns is not used, since T3 0.1.9 points it at its hosted app (`app.t3.codes`), which doesn't reach a self-hosted T3. The snapshot exposes only the team's T3 origin (`nativeT3Origin`). A T3 browser may still need its own pairing to show the thread.

A delivery waiting for an approval links to its run the same way, since approving happens only in T3: `GET /api/teams/:teamId/deliveries/:deliveryId/link` (a person's session and the channel's read access) reads the delivery's run through the same connection and returns `{url}`, that link or null (also before the run is in T3); any native failure is the same generic 503.

## Team MCP

Team MCP is a standalone agent-only service over Kinmesh's repositories, separate from T3's MCP. It uses `@modelcontextprotocol/sdk` stateless Streamable HTTP with Zod schemas and adds no tables.

### Setup

```dotenv
KINMESH_DATABASE_URL=postgres://…/kinmesh   # the hub's database
KINMESH_S3_ENDPOINT=…                       # the hub's file store, and its KINMESH_S3_* key
KINMESH_TEAM_MCP_PORT=3001
KINMESH_TEAM_MCP_ORIGIN=http://127.0.0.1:3001
KINMESH_TEAM_MCP_CONCURRENCY=16             # 1–64
KINMESH_TEAM_MCP_ENDPOINT=http://127.0.0.1:3001/mcp   # for team:smoke
KINMESH_TEAM_MCP_TOKEN_FILE=.store/team-agent.json    # for team:smoke
```

```sh
npm run team:mcp     # separate process, same database as the hub
npm run team:smoke   # read-only SDK check: initialize, ping, list, channel read
```

Issue the agent a grant with only the scopes it needs ([scopes](collaboration.md#grants-and-scopes)); the agent page issues one with channel and task scopes, and says where it goes: `KINMESH_TEAM_MCP_ORIGIN` plus `/mcp`, read by the hub too. A hub on loopback without it says the local default; a deployment that doesn't set it serves no Team MCP, and the agent page offers no token. Save it as `{"token":"…"}` in a 0600 file. The service applies migrations, needs no setup or session secret, and prints no credentials or content. The smoke CLI rejects unsafe token files, endpoints and redirects and prints fixed PASS/FAIL.

### Transport and authority

`POST /mcp` creates and closes an SDK server per request; there are no sessions, streams or resumption, and GET/DELETE return 405. Every request needs `Authorization: Bearer <agent-token>`; missing, expired, disabled or revoked credentials get 401 with `WWW-Authenticate: Bearer realm="kinmesh-team"`. Each tool call resolves the bearer again, and repositories check scope, team, channel and task authority in their transaction. The team comes only from the grant; the actor never comes from arguments, metadata or roles. Human cookies and actor headers are rejected. Accept, rework, cancel, editing a task, membership and credential administration are not offered. Network limits are in [security](security.md#team-mcp).

Remote clients reach the loopback listener through a same-host HTTPS reverse proxy: set `KINMESH_TEAM_MCP_ORIGIN=https://team.example` and use `https://team.example/mcp`. Team MCP authenticates with Kinmesh bearer grants, not OAuth; OAuth-only clients cannot connect.

Command fields are channelId, taskId, operationKey and expectedVersion; the tool names the action. `team_attachment_read` answers `{attachment, encoding, content}` for a file up to 1 MB: UTF-8 text as it is, anything else as base64; a larger file is refused. It is how an agent reads a file when its thread has no folder Kinmesh reaches (no space); Team MCP reads the bytes from the [file store](operations.md#the-file-store) (`KINMESH_S3_*`). Inputs, receipts, cursors and transitions are those of the [HTTP API](collaboration.md). Results carry `structuredContent` and the same JSON as text:

```text
{"result":{"ok":true,"data":<validated DTO or page>}}
{"result":{"ok":false,"error":{"code":"forbidden","message":"Permission denied"}}}
```

Expected failures set `isError: true` with a fixed code (`invalid_input`, `unauthenticated`, `forbidden`, `not_found`, `conflict`, `internal`) and no protected data; a refusal of `team_task_open_pull_request` or `team_task_read_repository` that says what to change adds its `reason` ([opening a pull request](collaboration.md#opening-a-pull-request), [reading a repository](collaboration.md#reading-a-repository)). Those two tools are the ones Team MCP does not answer from the database: each sends the request to the hub at `KINMESH_ORIGIN` (default `http://127.0.0.1:3000`) with the agent's own credential, because only the hub holds the team's GitHub App key, and answers with the hub's answer. Unknown tools and invalid schemas get the SDK's standard errors. A network failure is never proof of denied authority. Retry an ambiguous mutation with the same key and input. Every authenticated request records the agent's Team MCP presence for the workspace; presence is evidence, not authority.

### Provider configuration

A provider reaches Team MCP with the URL and the agent's bearer credential, configured through the provider's own supported settings, and lets Team MCP's tools run without asking a person: Team MCP already bounds each one by the grant's scopes, the agent's responsibility for the task and the rule that no agent accepts work, so an approval adds a click and no safety. T3's `t3_thread_launch` has no field for per-run MCP credentials, and T3 offers no interface, over MCP or its CLI, to make a provider, so each agent runs on a provider instance of its own that a person adds in T3 (Settings → Providers). Kinmesh never edits T3's settings. Never treat model feedback as human acceptance.

**Codex, configured by Kinmesh.** Where a [space provisioner](operations.md#the-space) runs beside T3 and Team MCP is served, each agent has its own Codex home there, which Kinmesh keeps. The agent page's model step names it: a person adds a Codex provider in T3 with that folder as its `CODEX_HOME` and chooses its model. Connecting the agent then issues a Team MCP credential for it (label `Team MCP (Codex)`, the channel and task scopes) and has the provisioner write the home's `config.toml`; the credential reaches no browser, log or response, the one it replaces is revoked once the new one is written, the hub renews it like the [worker's](security.md#hub-held-worker-secrets), and disconnecting revokes it. The home shares the T3 machine's Codex sign-in. When the home cannot be written, connecting says so and keeps no new credential.

**Configured by hand.** Without a provisioner, for an agent whose provider is Codex, the agent page issues the credential as the lines to add to that instance's `config.toml`:

```toml
[mcp_servers.kinmesh]
url = "<Team MCP URL>"
http_headers = { Authorization = "Bearer <credential>" }
default_tools_approval_mode = "approve"
```

Either way it is this configuration. Codex reads it when it starts, so a change takes effect once T3 starts the provider again. For another provider the page gives the credential alone, to configure the same way through its own settings.

Agents connected from the workspace may run on any provider T3 offers; Team MCP is optional for them. Operator-configured worker bindings assert with `externalTeamMcpConfigured: true` that their isolated provider was configured; Kinmesh cannot verify that remotely.
