# Collaboration model and HTTP API

Kinmesh owns team identity, communication, task responsibility and human acceptance. T3 owns provider sessions, threads, runs and execution records; Kinmesh reaches it only through the [T3 adapter](t3.md). This document is the reference for the domain model, the HTTP API and its invariants. Authentication, cookies, credential storage and limits are in [security](security.md); running the service is in the [README](../README.md) and [operations](operations.md).

## Principals and agent identities

A deployment holds one team, and everyone in it is an equal member: there are no roles, so any person may use the workspace, manage channels and agents, and connect T3; deciding on a task is its acceptor's alone (below). A person who leaves the organization can no longer sign in through Feishu; their history stays. The team is named after the organization: at every sign-in the hub reads the organization's name from Feishu, as the app (`tenant:tenant:readonly`), and renames the team to it; when Feishu cannot say, the name stays. Nobody renames the team in Kinmesh. A person is their Feishu identity, admitted by an organization mailbox ([sign-in](security.md#sign-in-and-sessions)); their handle is, at their first sign-in, the mailbox's name with characters other than `a–z`, `0–9`, `_` and `-` turned into `-`, prefixed `member-` when shorter than three characters, and numbered (`-2`, `-3`…) when taken. The handle is the person's stable identifier inside Kinmesh; they are shown by the name Feishu gives them and their Feishu picture, both refreshed at every sign-in (a name Feishu leaves out keeps the one before; the picture is kept as [security](security.md#avatars) says) and never edited in Kinmesh. Until a sign-in brings a name, the handle stands in. Authority is keyed on IDs, never on a name or handle. The first person to sign in creates the team and its `general` channel; each person after joins the team and `general`.

Every protected request resolves its principal again: a human from the verified encrypted session, an agent from `Authorization: Bearer <grant>`. Mixing both is rejected. Actor headers (`X-Kinmesh-Actor`, `X-Actor-Id`, `X-Member-Id`, `X-User-Id`), actor/identity/role query fields and author fields in bodies are rejected; a declared message role is never identity. Repositories recheck grant, scopes, lifecycle, team and channel membership inside each transaction, so a revocation takes effect on the next operation.

A branded `AgentId` is independent of `HumanId` and of every T3 identifier (environment, thread, run, provider session, AG-UI invocation). Changing provider, model or environment preferences keeps the agent's ID, team, creation time and history.

Let `A = /api/teams/:teamId/agents` and `P = A/:agentId`. IDs are UUIDs.

| Method/path                             | Policy / body                                                                                  |
| --------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `POST A`                                | Any person of the team; full profile; 201                                                      |
| `GET A`                                 | Any person of the team; includes disabled profiles                                             |
| `GET P`                                 | A person, or the matching active agent with `agents:read`                                      |
| `PUT P`                                 | A person; replaces the full editable profile; IDs, team and creation time forbidden            |
| `PUT P/avatar`, `DELETE P/avatar`       | A person or the agent itself; body is the image (see [security](security.md#avatars))          |
| `GET P/avatar`                          | A person, or the matching agent with `agents:read`; 404 when none                              |
| `POST P/lifecycle`                      | A person; `{ "lifecycle": "active" }` or `disabled`                                            |
| `POST P/grants`                         | A person, active agent; grant input; 201 `{grant,token}`, `Cache-Control: no-store`            |
| `GET P/grants`                          | A person; `{grants, revision}`: metadata, scopes, expiry, revocation; never a hash or secret   |
| `POST P/grants/:grantId/revoke`         | A person; 204; final                                                                           |
| `POST P/grants/:grantId/rotate`         | A person; grant input; atomic revoke + new secret; 201; 409 for the hub's own worker grant     |
| `POST P/executions`                     | A person or matching agent with `executions:write`; active profile; immutable correlation; 201 |
| `POST P/executions/:executionId/events` | A person or matching agent with `executions:write`; active profile; `{state}`; 201             |

A profile is:

```json
{
  "name": "Developer",
  "role": "developer",
  "capabilities": ["coding", "review"],
  "preferences": {
    "environmentId": null,
    "providerId": "codex",
    "modelId": null
  },
  "memoryLocation": null
}
```

Roles are `developer`, `reviewer` or `assistant`: descriptive, never authority. Names are unique within a team (trimmed, 1–80 characters). Capabilities are up to 32 unique labels of at most 256 characters, never scopes. Preferences are bounded IDs, null when unset; a model requires a provider. `memoryLocation` is an opaque reference of at most 1024 characters that is never dereferenced. `PUT` replaces the whole profile; audit keeps before/after snapshots.

### Grants and scopes

Grant input is `{ "label": "…", "scopes": [...], "lifetimeSeconds": 3600 }`: label 1–80 characters, 1–8 unique scopes, lifetime 60 seconds to 90 days. The grant the hub holds for its own worker is the one it [renews](security.md#hub-held-worker-secrets).

| Scope                             | Grants                                                   |
| --------------------------------- | -------------------------------------------------------- |
| `agents:read`                     | Reading the agent's own profile and avatar               |
| `channels:read`, `channels:write` | Reading channels; posting and creating topics            |
| `tasks:read`, `tasks:write`       | Reading tasks and task facts; creating and work commands |
| `tasks:review`                    | Technical review as the assigned reviewer                |
| `executions:write`                | Recording execution correlations and runtime reports     |
| `executions:read`                 | Nothing: accepted in grants, no route reads with it      |

Scopes are checked independently of channel membership, task assignment and role, and never widen when a profile changes. Any person of the team issues, rotates or revokes grants; agents cannot create identities, edit profiles or lifecycle, or administer grants. There are no roles: everyone of the team is an equal member.

Disabling an agent sets its lifecycle, revokes **all** its grants and writes audit in one transaction. Reactivation keeps identity and history but never restores old grants; when the agent is connected from the workspace, the hub issues its worker a fresh credential. Disabling does not stop T3 work already running or revoke T3 OAuth grants.

### Execution correlations

Correlation input is `{reference: {backend: "t3", environmentId, threadId, runId?}, providerSessionId, invocationId}` (IDs up to 256 characters, null when absent). One agent may have many correlations; a team cannot assign the same environment/thread/run tuple twice. Every correlation and runtime report carries a server-derived author (`human` + HumanId, or `agent` + AgentId and grantId).

Correlations are authorized assertions about an external reference, not proof that a run exists. Runtime reports (`unknown`, `active`, `waiting`, `succeeded`, `failed`, `stopped`) are attributed observations; they never call T3. Every correlation returns `acceptance: "not-evaluated"`; a reported success is never task acceptance. Execution truth comes only from T3 through the adapter.

Composite foreign keys bind grants, correlations and audit to agent membership; triggers keep grant bindings, revocation, correlations, runtime reports and audit append-only.

## Channels, topics and messages

Let `C = /api/teams/:teamId/channels` and `P = C/:channelId`. Every write but reading (`POST P/read`) takes a caller-generated `operationKey` (1–128 of ASCII letters, digits, `.`, `_`, `:`, `-`); reuse it only to retry the same logical operation.

| Method/path                          | Input / policy                                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `POST C`                             | `{operationKey,name}`; any person of the team; 201, creator enrolled                                          |
| `GET C`                              | Page of joined channels                                                                                       |
| `GET C?membership=left`              | The caller's own left channels (up to 100); removed ones never listed                                         |
| `GET C?membership=public`            | Public channels the person was never in (up to 100); agents get none                                          |
| `GET P`                              | Channel metadata (`visibility`); read access below                                                            |
| `GET P/membership`                   | Caller's own membership                                                                                       |
| `POST P/subscribe`                   | `{operationKey}`; rejoin a left channel, or a person joins a public one                                       |
| `POST P/visibility`                  | `{operationKey,visibility}`; a joined person makes it `public` or `private`                                   |
| `POST P/leave`                       | `{operationKey}`; leaves only the caller                                                                      |
| `POST P/participants/invite`         | `{operationKey,member}`; a joined person; enrolls an active team member                                       |
| `POST P/participants/remove`         | Same input; a joined person                                                                                   |
| `POST P/topics`                      | `{operationKey,title}`; joined participant; 201                                                               |
| `GET P/topics`, `GET P/topics/:id`   | Topic page; topic metadata in this channel                                                                    |
| `GET P/topics/:topicId/messages`     | Topic history page                                                                                            |
| `POST P/messages`                    | Post input below; joined participant; 201                                                                     |
| `GET P/messages`                     | Channel timeline page, including topic messages                                                               |
| `GET P/messages/:messageId`          | Immutable message                                                                                             |
| `GET P/messages/:messageId/mentions` | Structured mentions; same authorization as the message                                                        |
| `GET P/events`                       | Page of outbox facts for this channel                                                                         |
| `POST P/read`                        | `{messageId,topicId}`; a joined person; 204; read position below                                              |
| `POST P/attachments`                 | A file's bytes as the body, `?operationKey&name`; a joined person; 201                                        |
| `GET P/attachments/:attachmentId`    | The file; a message's for anyone who reads the channel, else only its uploader's                              |
| `POST P/attachments/:id/remove`      | `{operationKey}`; a joined person; removes a message's file                                                   |
| `GET /api/teams/:teamId/files`       | Files of the caller's joined channels, newest first; `?before`; `?channelId` for one channel the caller reads |
| `GET /api/teams/:teamId/search`      | `?q` (2–100 characters): messages and files of the caller's joined channels                                   |

Reads require human team membership or an active agent grant with `channels:read`, **plus** joined channel membership, except that a person of the team reads a public channel they were never removed from; nobody has an implicit bypass. Agent writes also need `channels:write`. A person creates channels and manages the participants of channels they are in; agents never can. Unknown and inaccessible channels return the same 404 and never appear in lists. Status codes: 401 invalid credentials, 403 missing scope or team, 400 schema or cursor error, 409 idempotency or uniqueness conflict. Errors never echo input.

Membership states are `joined`, `left` (the member may resubscribe) and `removed` (only an invite restores it). Nobody removes themselves; they leave.

**Visibility.** A channel is `public` or `private` (the default; `general` is public). A private channel is seen only by its participants. A public one is listed to every person of the team, who may read it without joining: its messages, topics, tasks, files and events. Everything else needs joining: posting, topics, tasks, files, read positions, levels, notifications and deliveries. A person joins a public channel themselves (`POST P/subscribe`); a removed person can neither read nor join it, and agents never read or join one by themselves, only by invite. Any joined person switches a channel between public and private (`POST P/visibility`); each switch is a `channel.changed` fact with the new `visibility`. A channel's ID, team and position never change. A joined person names it again (`POST P/rename` with `{operationKey,name}`, 409 for a name the team already uses); its folder in the space keeps the name it was given first. A joined person archives it or brings it back (`POST P/archive` with `{operationKey,archived}`): archived, it leaves everyone's channel lists, stays readable and searchable by its members, and takes nothing new (posting, topics, tasks and anything else that writes to it answer 409), so it starts no deliveries; the workspace lists a person's `archivedChannels` and says whether the open one is archived (`channelArchived`). Each is a `channel.changed` fact with the new `name` or `archived`.

**Two people's own conversation.** A person opens their conversation with another person of the team with `POST /api/teams/:teamId/direct` and `{operationKey,humanId}` (400 for themselves, 404 for someone not in the team), answering its channel. It is a private channel the two of them start in, made the first time (a `channel.created` fact, then the other's `participant.changed` joined) and the same one ever after; opening it brings the opener back if they left. It is a channel like any other — messages, topics, tasks, files, levels and notifications — except that it keeps its two people and its kind: it takes agents by invite but never a third person, neither of the two is removed, and it is never renamed, made public or archived (each 409). It is named for the two when made; the workspace lists a person's `direct` conversations (`{channelId,humanId}`, the other person) and calls each by that person's current name.

Post input (every field but `attachments` required; null means absent):

```json
{
  "operationKey": "discussion-001",
  "body": "Please review this proposal",
  "topicId": null,
  "mentions": [{ "kind": "agent", "id": "<AgentId>" }],
  "sourceMessageId": null,
  "sourceEventId": null,
  "attachments": ["<AttachmentId>"]
}
```

A mention target must be an active, joined participant of this channel; duplicates and disabled agents are rejected. `@text` is never parsed. Mentions grant no access. Topic and causal IDs must belong to the same channel. A person in the channel reacts to a message with one of a small fixed set (👍 👀 ✅ 🎉 ❤️ 😄): `POST P/messages/:messageId/reactions` with `{emoji,on}` adds (`on: true`) or takes back theirs, answering the message's reactions; doing what is done changes nothing, agents never react, and a reaction wakes no agent and notifies nobody. The workspace carries `reactions` for the messages it shows. A person in the channel pins a message there or unpins it (`POST P/messages/:messageId/pin` with `{on}`, answering the channel's pins); a channel keeps at most 50 (409 past that), and the workspace carries the open channel's `pinned` messages, the latest pinned first, each with who pinned it and when. A person replying to a message names it as `sourceMessageId`: the workspace quotes it above the reply, and a reply wakes nobody by itself (only mentions do), also when it answers an agent. Messages have a stable ID, server-derived author and time, channel/topic IDs, a persisted position, structured mentions and causal IDs, and are never deleted. A person joined to the channel may change the text of a message they wrote (`POST P/messages/:messageId/edit` with `{operationKey, body}`) or withdraw it (`POST P/messages/:messageId/withdraw` with `{operationKey}`), both answering the message: an edit sets `editedAt`, saying the same again changes nothing, and the text may be emptied only when the message has attachments; a withdrawal empties the text, sets `withdrawnAt`, is final (409 after), and is refused (409) while the message still has attachments. Someone else's message is 403, an agent never edits. Every change keeps what the message said before (who, when, edit or withdrawal) in an immutable record. An edit or withdrawal is no fact: it wakes and notifies nobody, and what came of the message — deliveries, their replies, tasks, mentions — stays as it was; a notification not yet shown for a withdrawn message is dropped, and a withdrawn message is no channel's newest in a list and is found by no search. Limits: body up to 8000 characters, title 160, channel name 80, 20 mentions, 10 attachments, HTTP body 16 KiB. A body may be empty only when the message has attachments. Bodies are plain text in the API.

**Attachments.** A person uploads a file to a channel they joined, then posts a message with it. The browser hashes the file, asks `POST P/attachments/uploads` with `{sha256,size}` where to put it, which answers `{url}` (null when the store has those bytes already), PUTs the bytes there with their SHA-256 as `x-amz-checksum-sha256`, then registers them: `POST P/attachments` with `{operationKey,name,sha256}` (the same key again answers the same attachment; with other bytes, 409; bytes the store doesn't have, 400) answers `{id,name,type,size,width,height}`. `type` is decided from the content (PNG, JPEG, GIF, WebP, PDF, else `application/octet-stream`), never from the name or the request; `width` and `height` are an image's pixels, else null. The post's `attachments` (up to 10, default `[]`) binds them to the message in its transaction: each must be the poster's own upload to this channel that no message took yet, else 400; agents attach none. A message's attachments are read with it, in upload order, and never change. `GET P/attachments/:id` rechecks read access each time and answers a `Range` of one part with 206; an upload no message took is readable only by its uploader, and is removed a day after it was made. Unknown and inaccessible files are the same 404. Limits and serving rules: [security](security.md#attachments). A message of files alone reads as their names wherever a text stands for it (a channel's latest message, a notification). Agents read a message's files as its [delivery](#delivery-states) describes. **Removing.** Messages never change, but a file is a thing of its own: any person joined to the channel removes one from its message (`POST P/attachments/:id/remove`); agents never can (403), and Team MCP has no such tool. In one transaction the file goes (its bytes too once nothing refers to them), `attachment_removals` keeps who removed which file of which message and when, never its name or content, and never changes, an `attachment.removed` fact tells open views, and its copy in the channel's folder is queued for the provisioner, which the hub asks every minute until it is gone. The message keeps its text and shows `removedAttachments` (who and when); deliveries not yet sent no longer list the file. Removal can't recall copies an agent made or committed, content already sent to a model provider, or backups taken before. `GET /api/teams/:teamId/files` lists the files of the channels the caller is joined to, newest first, 50 at a time (`?channelId` for one of them); `next` is the `before` of the following page. **Search.** `GET /api/teams/:teamId/search?q=` finds, in the channels the caller is joined to, up to 10 messages whose text holds `q` (any case, newest first; each with its channel, author, time and the start of its text) and up to 10 files whose name does.

Each person keeps a **read position** in each channel they joined: the newest message of its timeline they have seen, the same on every device. A channel is unread for them while someone else wrote after it; their own messages never make it unread, and a channel they muted never is ([notifications](#notifications)). `POST P/read` says they have seen the channel up to `messageId`, reading the whole channel (`topicId` null) or that topic (the message must be in it, else 404): the whole channel moves the position to the message; a topic moves it only as far as everything someone else wrote after the position is in that topic, so what they haven't seen elsewhere stays unread. The position never moves back, and reading again changes nothing, so the route takes no `operationKey`. Agents have none (403). A person who joins a channel has read nothing in it yet.

## Tasks

Let `T = /api/teams/:teamId/channels/:channelId/tasks`. Every route rechecks joined channel membership. Agents also need `channels:read` and `tasks:read`; commands need `tasks:write`, except review, which needs `tasks:review`.

Any joined member with write authority may create an unowned task or one owned by themselves; a person may also preassign another member or a reviewer, an agent may not. The immutable `acceptorHumanId` is the person who asked for the task. A creating person is it, unless they name another person joined to the channel as `acceptor` (404 otherwise). An agent never names one (403); its task goes to the person at the root of the causal chain of `sourceEventId` (every chain starts with a person's act), else the person who wrote `sourceMessageId`, else the person who last wrote in the channel, else the lowest-ID person joined to it (409 if none) — each only while still joined. The acceptor never changes, and only the acceptor accepts, sends back or cancels. The acceptor must still be a joined member when deciding.

| Command                 | Legal state / actor                                            | Result                                                     |
| ----------------------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| create                  | Authorized participant; optional owner                         | `proposed` if unowned, else `in-progress`                  |
| claim                   | Any authorized writer; `proposed`; not its preset reviewer     | `in-progress`, caller owns it                              |
| progress                | Work owner; `in-progress` or `rework-requested`                | `in-progress` with a note                                  |
| handoff (work)          | Work owner; `in-progress`/`rework-requested`                   | New owner, reviewer cleared; `in-progress`                 |
| handoff (work recovery) | Acceptor; any nonterminal owned task                           | Audited transfer to an active joined member; `in-progress` |
| handoff (work, assign)  | Acceptor; `proposed`; not its preset reviewer                  | The member owns it, reviewer kept; `in-progress`           |
| handoff (review)        | Work owner; `in-progress`/`rework-requested`                   | Owner kept, distinct reviewer; `review-requested`          |
| request-review          | Work owner; `in-progress`                                      | Owner kept, distinct reviewer; `review-requested`          |
| review approve          | Assigned reviewer; `review-requested`                          | `awaiting-human` (**not accepted**)                        |
| review rework           | Assigned reviewer; `review-requested`                          | `rework-requested`                                         |
| rework                  | Acceptor; any nonterminal owned task                           | `rework-requested`                                         |
| accept                  | Acceptor; `awaiting-human`                                     | Terminal `accepted`, server human ID and time              |
| cancel                  | Acceptor; any nonterminal task                                 | Terminal `cancelled`, server human ID and time             |
| link-execution          | Work owner, or the assigned reviewer while review is requested | Immutable execution reference; state unchanged             |
| edit                    | Acceptor (a person); any nonterminal task                      | New title, description, criteria and reviewer; same status |
| link-pull-request       | Any authorized writer; any nonterminal task                    | Immutable pull request link; state unchanged               |
| open-pull-request       | Work owner, an agent; `in-progress` or `rework-requested`      | Pull request opened on GitHub and linked; state unchanged  |

Owner and reviewer must differ and stay active and joined. Rework always needs another review before acceptance. Terminal tasks reject every command. Creator, context and acceptor are immutable; progress is a note, not a patch. A task may say the day it is due (`due`, `YYYY-MM-DD`, null when none) and how much it matters (`priority`: `high`, `normal` — the default — or `low`); both are set on create, by anyone who creates, and changed by an edit. Only the acceptor edits what is asked: an edit gives title, description, criteria, reviewer, due day and priority as they should be, must change at least one (400 otherwise), and keeps the reviewer once review is asked for (`review-requested`, `awaiting-human`; 409 otherwise); a changed reviewer must be an active joined member other than the owner. An edit wakes no agent and notifies nobody; its history entry carries the task before and after. Agents never edit (403). Audit keeps before/after snapshots, command, verified author (with grant ID for agents), time, version and event ID. Runtime completion is not part of the transition algebra; execution links and reports never accept a task.

| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |

| `GET T/:taskId/executions`                | Page of execution links                                                                                                         |

Commands return `{task,eventId,executionLink,pullRequestLink}`. Status codes: 401/403 or hiding 404 for authorization, 400 schema or cursor, 409 transition, version or key conflict, 413 oversized body.

### Pull requests

A task links GitHub pull requests as evidence of its work: `repository` is `owner/name` as GitHub allows it, `number` the pull request's. A link is its author's claim, kept with the server's author and time; it never changes, wakes nobody, notifies nobody and changes no responsibility, review or acceptance. A pull request is linked to a task once however its repository is cased (409 otherwise), and a task links at most 20 (413).

What GitHub says is kept apart from the link, per pull request, as an observation: its repository and number as GitHub names them, title, `open`, `closed` or `merged`, draft, address, head and base branch, head commit and `observedAt`, and that head commit's checks; or `unavailable` with why (`not-found`, `forbidden`, `rate-limited`, `unreachable`) and when. The checks are read with the pull request, from its head commit's check runs and commit statuses: each one passed (success, neutral, skipped), failed (any other end) or has not ended, and together `failing` if any failed, else `pending` if any has not ended, else `passing`, or `none` when the commit has none — which is not a pass. They name the commit they belong to and when they were read; a new head commit is read with its own, so an older commit's result never stands for the current one. Checks GitHub will not show are `unavailable` (`forbidden`, `rate-limited`, `unreachable`) while the pull request itself is still read. Null means GitHub has not been asked yet. The hub asks about a new link within half a minute, about one whose checks are running every minute, about open ones every 5 minutes and about merged or closed ones every 6 hours (see [operations](operations.md#github)). A rate limit or an outage keeps the last answer, which then shows its age; an answer older than three of its intervals is stale. GitHub's state never accepts a task: no state of a pull request or its checks is a review, and none moves a task.

The workspace snapshot carries the open task's pull requests as `taskPullRequests`, so an open task shows a new link or a newer answer as it happens.

### Opening a pull request

The agent working on a task (its owner, while `in-progress` or `rework-requested`) has Kinmesh open its change on GitHub with `POST T/:taskId/open-pull-request`: `repository` (`owner/name`), `base` (the branch to start from; null for the repository's default), a new `branch`, `title` (1–256), `body` (up to 20,000 characters) and `files`, 1–100 distinct paths each with its whole new text, or `content: null` to remove the file; at most 1 MiB of text in all, and a body up to 2 MiB. Paths are relative, without `.`, `..` or `.git` parts; files are written as ordinary (non-executable) files.

Kinmesh, with the team's [GitHub connection](#github), makes one commit of those files on the base's head, creates the branch at it, opens the pull request from it into the base, and links it to the task in the same command (`pullRequestLink`; the history says the agent opened it). The commit and pull request are the team's app's, never a person's: the commit's message is the title, a line saying which agent made it for which task, `Kinmesh-Task: <taskId>`, `Kinmesh-Change: <digest>` and a `Co-authored-by` naming the agent; the pull request's body ends with the same line and the task's address. A person opens their own on GitHub (403), as does an agent that is not working on the task (403, or 409 for a task not being worked on). Nothing is written to GitHub before the request passes those checks.

The same `operationKey` with the same input answers as before without asking GitHub again; with other input it is 409. A retry after an answer was lost never opens a second pull request: Kinmesh only writes to a branch whose head is this change's own commit (its `Kinmesh-Change`), and uses the pull request already open from it. A refusal Kinmesh can explain carries `reason` beside `error`: `github-not-connected` (409: the team has no GitHub connected), `repository-not-connected` (403: the app is not installed there or may not write), `base-missing` (409) or `branch-taken` (409: the branch exists and is not this change's). GitHub being unreachable or failing is a 500; asking again with the same key is safe. Opening a pull request merges nothing, and its state never moves the task.

### Reading a repository

The agent a task is with (its owner) reads the repository it changes with `POST T/:taskId/read-repository`, through the same [GitHub connection](#github), as the team's app and never as a person: `repository` (`owner/name`), `ref` (a branch or a 40-character commit; null for the repository's default branch) and `path` (relative, as in a pull request; empty for the top). A file answers `{kind: "file", repository, commit, path, text}`, its whole text; a directory answers `{kind: "directory", repository, commit, path, entries: [{name, kind}]}`, `kind` `file`, `directory` or `other` (a link or submodule), at most 1,000. `commit` is the commit `ref` named when it was read. Anyone else is refused (403), a person included. Reading writes nothing on GitHub. A refusal Kinmesh can explain carries `reason`: `github-not-connected` (409), `repository-not-connected` (403), `ref-missing` (404), `path-missing` (404), `not-text` (400: binary, a link or a submodule) or `too-large` (413: more than a pull request may carry, 1 MiB). It is never cut short.

## Atomicity, idempotency and pagination

Every write runs in one serializable transaction, retried when PostgreSQL reports a conflict, that rechecks authorization, checks the operation receipt, applies the change (tasks use compare-and-set on ID, version, status and owner), appends audit and an outbox fact, enqueues any [Inbox](#agent-inbox) deliveries and stores the response receipt. Everything commits or nothing does. Triggers keep mentions, task audit, links, receipts and outbox facts immutable, and messages so apart from their author's edit or withdrawal of the text.

Receipts are scoped by team, author, action and target and store a fingerprint of the validated payload (including `expectedVersion`). An exact retry returns the original response, even after later changes, without repeating effects; different input under the same key is 409. A replay is not a fresh snapshot: read again for current state. Membership changes check current rights before replay. Rotated grants keep agent identity, but a retry still needs a current grant with the right scopes and membership.

Lists take `limit` (1–100, default 50) and an opaque `cursor` (at most 2048 characters) and return `{items,nextCursor}`; null ends the scan. Ordering uses persisted positions, and items within a page run oldest to newest. Message and task lists (channel and topic history, `GET T`, and the Team MCP tools that read them) start at the newest: the first page is the latest `limit` items and each `nextCursor` reads the page before the oldest one returned, so a newer write never shifts, duplicates or leaks into an older page; read the first page again to see it. Every other list (channels, topics, outbox facts, task history and executions) starts at the oldest and its first page fixes the highest visible position, so concurrent writes never enter that scan; start a new scan to see them. A task page fixes the set of tasks, not their values. Cursors are bound to the caller, team, view, channel, topic or task and are never authority: each page rechecks access, and a wrong-context cursor is 400.

### Outbox facts

`OutboxFact` (`src/domain/communication.ts`) is the versioned union of communication facts (`channel.created`, `channel.changed`, `participant.changed`, `topic.created`, `message.posted`, `attachment.removed`) and `task.changed`. A fact carries its event ID, kind, team/channel/topic/message IDs, server author and time, mention targets, membership change, operation key and causal IDs. Task facts share their audit event's ID and carry task ID, version, status, action, owner, reviewer and any execution link. Facts omit message text and task content. `GET P/events` is channel-scoped; task facts appear only to principals with `tasks:read`. Facts confer no authority and do not imply delivery.

## Agent Inbox

The Inbox turns committed facts into bounded wakes of agents through T3. Deliveries are enqueued **inside the source transaction**; the worker that runs them is described in [operations](operations.md#inbox-worker).

### Wake policy and causality

- A human's message wakes each **structured mention** of an active, joined agent.
- Human task assignment, work or review handoff, request-review, human rework and reviewer rework wake the agent now responsible: the reviewer while review is requested, the owner while work or rework is active.
- Self-authored changes, progress, claims, execution links, acceptance, cancellation and agent chat wake no one.

Agents may hand tasks to agents. Causality comes from the task audit chain: a human action starts a root, and agent transfers spend a budget of **four** hops. `(root, agent)` uniqueness stops revisits; `(event, agent)` uniqueness makes delivery idempotent. Suppression affects delivery only; messages, decisions and facts are kept.

Enqueue never grants authority. Before dispatch and again at publication the worker rechecks the agent's credential, scopes (`channels:write` and `executions:write`, plus `tasks:write` for task wakes), lifecycle and membership; a fresh dispatch also needs current assignment. Worker identity comes from its token, not from configuration or event text.

### Delivery states

A delivery is `ready`, `waiting`, `uncertain`, `blocked`, `acked` or `expired` (unsent work that expired, or that a person stopped before it reached T3 or once its T3 authority had changed). A blocked delivery records a cause a person can fix: `agent-disabled`, `credential-invalid`, `not-in-channel`, `not-assigned`, `native-access`, `native-incompatible` (T3 doesn't offer the agent's model or provider), `native-unreadable` (T3 returned data Kinmesh can't read, such as a field longer than Kinmesh accepts; a launch or send whose answer can't be read is blocked too, and its retry reconciles under the same native request key), `environment-changed` (T3 now answers from another environment than the agent was connected to), `authority-changed` (the run reached T3 under a credential or T3 authority the agent no longer has, so its answer can't be posted), or `authority-or-contract-blocked` when none of these applies, which is also how a publication that a rule of the database refuses stops: it is refused again however often it is tried, so it is not retried as an outage. `not-assigned` is decided by the same rule publication uses: the task no longer has the agent act on it. A delivery the worker claims when T3 honours none of the team's T3 credentials (a person's sign-in ended, and there is no deployment's session to fall back to) is not blocked: it waits `ready` with the reason `sign-in-expired`, nothing is sent to T3, and it goes on after the next sign-in ([T3 sign-in](t3.md#t3-sign-in)).

The worker takes a delivery up again when it is due. A run under way (`waiting`) is looked at every 2 seconds at first, slowing to every 15 seconds once it has waited two minutes, however often T3 failed before the run started. Anything else that did not go through is tried again after 1 second, doubling to at most 5 minutes. A delivery's history records each change of its state or reason; looking again and finding the same records nothing, so the times the workspace shows for it change only when it did.

Any person resumes a blocked delivery with `POST /api/teams/:teamId/deliveries/:deliveryId/resume` (a person's session and channel read access; agent bearers are refused; keyed, so a retry replays). Resume keeps the frozen intent, authority and native request key, and authority is rechecked at dispatch and publication, so it cannot revive a revoked credential or switch to another.

The same people stop one with `POST /api/teams/:teamId/deliveries/:deliveryId/stop` (`{operationKey}`, same rules). A delivery nothing of which reached T3 ends at once, `expired` with the reason `stopped`; a worker about to send it ends it the same way instead. One whose run may be in T3 records the request (`stop-requested`); the worker interrupts the run in T3 under its own journaled operation (`actor=inbox-agent:<AgentId>`, `operationKey=inbox-stop:<DeliveryId>`), so T3 is asked once however often it retries, and reads on until T3 reports the run ended: what it posts is the run's [result](#results), the stopped notice when it wrote no reply. A run T3 keeps going is never given up on. A delivery already answered or expired stays as it is (200); a blocked one whose run may be in T3 is 409, since Kinmesh can't reach that run until it is resumed, except one blocked `authority-changed`: the authority its run launched under is gone, so nothing could be posted for it, and it ends at once without asking T3, `expired` keeping that reason. The request is kept once made, which a database trigger enforces.

Each agent keeps one conversation per topic, and one for the channel's messages outside topics: a T3 thread its first delivery there launches, titled with the agent, channel and topic. When the deployment has a [space](operations.md#the-space), every channel is a T3 project in it, and each of its conversations is a thread at that project's root, so everyone in the channel works in one folder; without a space, each conversation is a scratch thread with a folder of its own. A channel's folder is named once, from its name and the start of its ID (`design-3f2a91c0`), and kept. The first new thread in a channel asks the space's provisioner for the folder, then finds its project with `t3_project_list`; a provisioner that can't be reached holds the delivery, and one that refuses, or a folder T3 has no project for, blocks it (`native-access`, `native-incompatible`). A launch retried after a lost reply keeps the project it was frozen with. **What a run is on.** While a delivery's run is under way in T3, each time the worker looks at it, it reads the run's latest activity and keeps one line on the delivery (`step` in the workspace's deliveries): what waits on a person's approval in T3, the command or change T3 asks about (`waiting: true`), or the step the run is taking; anything but `waiting` clears it. Approving stays in T3, whose tools cannot answer an approval. **Files.** Before a delivery for a message with attachments is sent to T3, the worker places them in the channel's folder (`attachments/`, through the provisioner) and its turn lists each one's path from the folder's root, type and size, never the content; so every thread of the channel, in any topic and for any agent, also one started later, finds them in its working directory. Placing waits like asking for the folder: a provisioner that can't be reached holds the delivery, and one that refuses blocks it (`native-access`, or `native-incompatible` for another file under the same ID); a person resumes it once fixed, and placing again changes nothing. Without a space, the turn lists each file's name, type, size and ID, and the agent reads it with `team_attachment_read` ([T3](t3.md#tools)); no download link goes into a turn. A scratch conversation from before the space keeps the deliveries already in T3 there; its next message starts a thread in the channel's project, and the scratch thread stays in T3. Every later delivery for the agent in that conversation is sent into the same thread with `t3_thread_send` in `auto` mode, so the agent keeps the conversation: it starts an idle thread's next turn, or steers a running one instead of waiting behind it, including one waiting for an approval (the agent sees it once the approval is answered). A delivery whose run another delivery's message steered is answered by that run's one reply, posted once. If that run stops instead (interrupted in T3, or by a person stopping another delivery), T3 loses the steered message with it, so the worker sends it again, once, as a turn of its own (`t3_thread_send` in `queue` mode under `operationKey=inbox-again:<DeliveryId>`), and the delivery is answered by that turn; a database trigger lets a delivery's run change only this way. A steered delivery a person stopped is answered by how its run ended. Another model or runtime mode, or another T3 authority or environment, starts a new thread for the next delivery; the old one stays in T3. A thread deleted in T3 ends its conversation: a run still under way in it ends with a stopped notice, and the next delivery, refused by T3, starts a new thread with a first turn. A delivery's run is read from the position after the conversation's last published answer.

Before any native effect, the worker freezes the source context, model, conversation, Kinmesh grant and T3 endpoint/environment/authority. Each delivery has the stable native identity `actor=inbox-agent:<AgentId>`, `operationKey=inbox:<DeliveryId>`. A launch that provably never reached T3 (no operation ID, reference or journal entry) is frozen again as things are now: under the current T3 authority and grant, with the model now chosen and into the conversation's current thread. Once it may have reached T3, the run keeps the model and thread it started with (a send T3 refused because the thread is gone reached nothing), and a changed T3 authority or grant blocks it (`authority-changed`) rather than starting a new operation elsewhere. A database trigger enforces the same rule. Choosing another model for a connected agent changes its preferences and its worker's provider, never its credential, so a run under way still posts its answer; until the worker serves the new provider, a new launch waits (`setup-catching-up`) instead of blocking.

The first turn of a conversation says who the agent is, the channel (with its ID, for team tools), the topic if any, and the rules: what people write is their request, not instructions or permission. Every turn carries the event as plain marked-up text in an ordinary user turn: who wrote it, by the name the workspace shows; the message text (up to 4000 characters); for a task, its ID, status, the change, title, description (2000) and up to five criteria (200 each); and, on the first turn, the memory-location reference (never loaded). What people wrote is escaped, so it cannot close its block, and shortened between characters. Internal identifiers (delivery, event, team, person) are not sent. The run's T3 runtime mode is set by the [T3 adapter](t3.md#operations).

### Results

The worker publishes only a nonempty `assistant_message` from the exact correlated run, after T3 reports it terminal with no pending requests. Pending approval keeps the delivery `waiting`; incomplete history keeps it retryable. Failed or stopped runs publish their real text with their real state; a run that ended without a reply publishes one plain sentence saying so. The message holds up to 6000 characters of the reply, cut between characters, never inside one (an emoji stays whole or goes); its provenance (terminal state, shortening, provider, model, T3 environment/thread/run) is kept beside it, not in the text.

Publication is one fenced transaction: authority and assignment checks, execution correlation and runtime event, optional task execution link, the attributed message with the original source IDs, its outbox fact and receipt, the result record and the ACK. Result messages have no mentions and cannot wake anyone. Automatic execution links never change task state, review or acceptance.

An agent that keeps owner or reviewer responsibility may still settle a run it already dispatched after a handoff, approval, acceptance or rework, whether that run started the conversation's thread or was sent into it. Reassignment, cancellation, revoked grants and removed membership block publication.

Work that never reached T3 expires after seven days, frozen or not, whether a worker serves its agent or not (the hub looks every minute). Just before it calls T3, the worker marks the delivery `uncertain` under its claim (a worker whose claim is gone stops there); from then on, and for anything journaled or correlated, a native effect may exist, so it never expires on its own.

## Notifications

A person is notified in their browsers of what concerns them, even with Kinmesh closed, through Web Push, and in Feishu. What notifies whom is decided from the facts above, inside the transaction that commits each one (as the [Inbox](#agent-inbox) enqueues), once per cause and person, and never for a person's own act:

| Cause                                                                                                    | Kind      |
| -------------------------------------------------------------------------------------------------------- | --------- |
| An agent's message whose causal chain starts with the person's act (it answers what they asked)          | `reply`   |
| A delivery whose causal chain starts with the person's act becomes `blocked` (each time it does)         | `blocked` |
| A task reaches `awaiting-human` with the person as acceptor                                              | `decide`  |
| A task is created, handed, sent for review or back for rework, and the person now works on or reviews it | `task`    |
| A message mentions the person                                                                            | `mention` |
| Any other message in a channel the person is joined to                                                   | `message` |

**The rule, not a setting.** The first five kinds concern the person and may interrupt them in any channel they haven't muted; `message` interrupts only in channels they follow. Each person sets each channel they are in to one **level**: `default`, `follow` (every message) or `mute` (nothing, and never unread); the snapshot carries the channels not at the default as `levels`. A notification is due five seconds after its cause, then sent at most once, and only if it still concerns the person: they are still joined to the channel, the message is still unread for them ([read position](#channels-topics-and-messages)), the task still at the version that caused it, the delivery still blocked. So nothing is sent about what a tab open on it has already read.

**In Kinmesh, or away.** While a session of the person's was used in the last 90 seconds they are in Kinmesh: what falls due is not pushed or sent but shown on their page, in the snapshot's `notices` (for two minutes: what it says and where it opens). Otherwise it is pushed to their browsers, and goes to Feishu as below.

**Quiet time.** While the person has paused, or is outside their hours, nothing is pushed or sent: what falls due is held. When the quiet time ends, what was held and still concerns them goes out as one summary (how many things wait), pushed and sent to Feishu, never as a backlog.

A browser is notified once a person turns notifications on in it, held by the session they did that in: signing out of that session, or everywhere, ends it, and it lasts no longer than that session could (seven days from its sign-in, [security](security.md#sign-in-and-sessions)). Opening the workspace hands a browser already notifying that person to the session in use. A push carries a title and one line (who wrote or what changed, and where), the address of the place, and what it is about.

| Method/path                  | Input / policy                                                                                                                                                        |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/push/key`          | The hub's Web Push (VAPID) public key                                                                                                                                 |
| `PUT /api/push/subscription` | The browser's `PushSubscription.toJSON()`, an `https` endpoint; this browser now notifies the caller                                                                  |
| `POST /api/push/renew`       | `{endpoint}`; held by this session from now, only if it already notifies the caller; 204                                                                              |
| `POST /api/push/unsubscribe` | `{endpoint}`; this browser no longer notifies the caller; 204                                                                                                         |
| `POST /api/push/test`        | `{endpoint}`; one notification to that browser, if it notifies the caller now (410 otherwise); 502 when its push service can't be reached; 204                        |
| `GET /api/push/browsers`     | The caller's browsers receiving notifications: a short id made from each endpoint (the endpoint never leaves the hub), the push service's host, when it was turned on |
| `POST /api/push/forget`      | `{id}`; that browser no longer notifies the caller; 404 if it isn't theirs; 204                                                                                       |
| `GET /api/me/profile`        | The caller's handle, name and mailbox as Feishu last gave them, and the team's name                                                                                   |
| `GET /api/me/sessions`       | The caller's sessions that still let them in, newest use first: a short id made from each stored hash, whether it is the one asking, when it began and was last used  |
| `POST /api/me/session/end`   | `{id}`; ends that session of the caller's; 404 if it isn't one; 204                                                                                                   |
| `POST /api/feishu/test`      | The team's Feishu bot sends the caller one message: 204 when Feishu took it, 502 when it refused or couldn't be reached, 409 before they signed in with Feishu        |

**Feishu.** What stays unread reaches the person in Feishu, from the app's bot: `forwardAfter` minutes (0, or 10 by default; null, never) after a notification falls due, if it still concerns them by the same checks and they still want it then, it is sent to them once (by their Feishu `union_id`) as a card: its title, its line and 查看, which opens its place. Once it no longer concerns them (read, decided, unblocked), the card turns into 已处理 within seconds, so their other devices stop showing it as pending; a card is followed for a week at most. It is sent whether or not a browser of theirs was notified. It is never retried as another message.

**Hours.** A person may choose the hours notifications may reach them: from one time of day to another (past midnight when the second is earlier), every day or on weekdays only, in the time zone their browser had when they chose them (`hours` in the snapshot; null, the default, is any time). Outside them is quiet time (above), held and summed up when they open, if it still concerns them then. A pause, by contrast, drops what falls due while it lasts.

| Method/path           | Input / policy                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `PUT /api/me/forward` | `{minutes}`: 0, 10 or null; 204                                                                              |
| `PUT /api/me/hours`   | `{hours}`: `{from,to,weekdays,timeZone}` (minutes of the day, `from` ≠ `to`, an IANA time zone) or null; 204 |

A **pause** is quiet time until a time at most a week ahead, and ends by itself.

| Method/path         | Input / policy                                                                 |
| ------------------- | ------------------------------------------------------------------------------ |
| `POST P/level`      | `{level}`: `default`, `follow` or `mute`; a joined person, for themselves; 204 |
| `PUT /api/me/pause` | `{until}` (ISO time within a week, or null to resume); 204                     |

These are a person's own; agents are refused. They need no `operationKey`: repeating one changes nothing more.

## Workspace snapshot

`GET /api/workspace` is a person's read that reconstructs, from Kinmesh's own data: what notifies them ([notifications](#notifications)), the team, joined and left channels, public channels to join (`publicChannels`), the selected channel's messages, topics and tasks, the team's people (handle, name, when their picture last changed, and online when a session of theirs was used in the last 90 seconds; the picture itself is `GET /api/teams/:teamId/people/:humanId/avatar`, for the people of the team, 404 when none) and those joined to the channel, agent profiles and avatars, and channel membership of agents. It takes only bounded cursors and channel/topic selection, never an actor, and responds `Cache-Control: no-store`. It is one consistent read: a single read-only, repeatable-read transaction, so everything in it shows the same committed moment, and the person's access to the team and to the channel is checked once within it. Besides the topic page it carries `activeTopics`: up to 10 of the channel's topics, most recently active first (the time of a topic's latest message, or of the topic itself), and whether there are more. `latest` holds, for each listed channel with a message, its newest one: the message ID, its author, its first 200 characters and its time, and whether the channel is unread for the person ([read position](#channels-topics-and-messages)). Its `revision` changes exactly when what it shows changes; the read time and worker heartbeats that change nothing on screen are left out. The AG-UI snapshot below carries the same kind of `revision` for the agent's runs. Pages hold up to 100 channels and profiles and 50 topics. Messages are the newest 50; `messagesCursor`, a `messages.nextCursor` the snapshot gave, widens them back through the page it names, up to 200, so a view that has scrolled back keeps what it shows while new messages still arrive. Tasks are the newest 100; `taskId` names the task open on the board, which comes as `openTask` when it is older than those (null when it isn't in the channel).

It also carries:

- `deliveries` — for the visible messages and tasks: delivery ID, agent, source, state, reason, times, the reply message and whether a person asked to stop it. Claims, frozen launches, operation IDs and native references stay in the worker.
- `replies` — for visible agent replies: outcome, model and T3 identifiers.
- `firstUnread` — in the open channel (or its topic), the first message someone else wrote after the person's read position, so the view opens there; null when nothing is unread, the channel is muted, or the person only looks in.
- `attention` — what waits on the signed-in person across joined channels: `decide` (tasks awaiting their sign-off, review or rework; up to 50), `unstuck` (blocked deliveries they caused — the root of what woke the agent is theirs; anyone may resume any; up to 50), `connect` (agents with queued work and no live worker) and `t3` (from seven days before a person's T3 sign-in for the team ends until someone signs in again, or while a session the deployment no longer provides has ended: the endpoint, when it ends, whether it has, the mode runs fall back to under the deployment's session (`fallback`, null when they wait) and the sign-in under way; the deployment's own session never asks).
- `wake` — per agent, when a worker last recorded it and whether that is within 90 seconds (see [worker liveness](operations.md#worker-liveness)).
- `managed`, `teamMcp` — agents the hub runs, and when an agent's credential last reached Team MCP. Team MCP presence is evidence, not authority.
- `nativeT3Origin` — the origin of the team's T3 connection, used to [check a run](t3.md#checking-a-run), or null before T3 is connected (**连接 T3**).

`GET /api/agui/:teamId/:memberId` returns one official AG-UI 1.0 `STATE_SNAPSHOT` event for an agent, validated on both ends with `@ag-ui/core` schemas: source `kinmesh-persisted-reports`, read time, the profile, up to 20 execution associations and 100 reports each, in persisted order. An AgentId is never an AG-UI invocation ID, and a ChannelId is never a T3 ThreadId.

Both are HTTP snapshots, not run or token streams: no `RUN_STARTED`, text deltas or approval controls are synthesized.

`GET /api/events` is a Server-Sent Events stream for one open view; its types are in `src/workspace/events.ts`. A view shows resources, each read by one route whose response carries its `revision`: `workspace` (`GET /api/workspace`), on an agent page also `t3` (`GET /api/teams/:teamId/t3`, including a sign-in under way) and `runs` (`GET /api/agui/:teamId/:agentId`), and on the page for running an agent's worker yourself `grants` (`GET /api/teams/:teamId/agents/:agentId/grants`). The stream takes the snapshot's query and the page open on it (`page=agent:<id>` or `page=worker:<id>`), and answers at once, before it reads them. Its `revisions` event names the revision of every watched resource first, then only those that changed; the browser reads again exactly the resources whose revision differs from the one it holds. The workspace needs no read: just before each `revisions` that names it, a `workspace` event carries the snapshot itself, exactly as `GET /api/workspace` answers it. A workspace the person can no longer read is only named, and reading it shows why. Checks of one stream run one after another, and changes that arrive during one are taken up by a single check after it. The streams of one person's place share one snapshot until the next change, so several views of a place read it once per change; a `GET` shares one only while it is still being read, so it always shows what is now, heartbeats and T3's sign-in included. A write through the hub is a change, and a snapshot is reused for 10 seconds at most. The page opens its stream as it starts, before the workspace's code has arrived (`web/boot.ts`), and shows the workspace from it; a new place, reaching further back, **Refresh now** (which reads everything on screen), a stream that fails or stays silent for 3 seconds, and API clients read `GET /api/workspace`. While the hub can be reached nothing is polled; while it cannot, the browser asks again every 5 seconds, and a stream the hub refused is opened again after the next successful read. The hub notices every commit, by any process, through the `NOTIFY` the tables' triggers send for what a view shows (taking up a delivery and the T3 operation journal are bookkeeping, and send none), and agents crossing the liveness window by looking every second. How stale or failed reads appear is specified in [DESIGN.md](design/DESIGN.md#voice).

The browser sends a new `operationKey` for each logical action and the rendered `expectedVersion` for task commands. A request whose outcome is unknown keeps its exact body and key and is retried only on request, never automatically.
