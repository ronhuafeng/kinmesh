# External T3 adapter (Issue #2)

Kinmesh's execution authority remains **unmodified external T3**, independently installed/upgraded. This adapter uses official MCP SDK Streamable HTTP and OAuth only. No T3 implementation code, private package, database, WebSocket or host-CLI execution fallback is included. Tool schemas are wire-contract fixtures, not vendored runtime code. Reuse → Adapt → Extend → Build: SDK for transport/OAuth, Zod + Ajv for boundary validation, and the existing Drizzle/SQLite transaction layer for owned operation intent. The small journal fills the cross-system atomicity gap; it is not another execution harness or queue.

## Owner sign-in: no copy/paste bearer credentials

Use Node 24 on a trusted owner workstation with a working local browser. Install this feature branch, then configure a private `.env` (generated by the existing `npm run setup`, then edit locally). Never paste its contents into issues, chat, logs or CI output.

```dotenv
KINMESH_T3_ENDPOINT=https://your-owner-private-origin.example/mcp
KINMESH_T3_AUTH_FILE=.store/t3-owner-oauth.json
KINMESH_T3_READ_AUTH_FILE=.store/t3-read-oauth.json
KINMESH_T3_PROVIDER=codex
KINMESH_T3_MODEL=your-advertised-model-id
KINMESH_T3_LIVE=1
KINMESH_T3_LIVE_DATABASE=.store/t3-live.sqlite
KINMESH_T3_LIVE_REPORT=.store/t3-live-report.json
```

```sh
npm ci
npm run t3:auth
# Approve the sign-in in your browser; choose Supervised, not Full access.
KINMESH_T3_AUTH_FILE=.store/t3-read-oauth.json npm run t3:auth
# Approve the second sign-in as Read only.
npm run test:live
```

`npm run t3:auth` uses SDK discovery, dynamic registration, S256 PKCE, a random state and a loopback-only callback at `127.0.0.1:49871/callback`. It opens the authorization page without printing the URL and validates callback state and issuer before SDK code exchange. Complete owner authentication through the existing Runner private browser link when needed; obtain/enter pairing credentials only in T3's private native UI. The callback must be on the computer opening the browser. Running this CLI on a headless Runner does not make your workstation's localhost callback reachable; use a local workstation checkout instead. Browser launch/approval absence fails; no manual token-paste fallback exists.

Tokens/client registration and the pinned environment identity go into the configured private file using an atomic mode-0600 replacement. Loading rejects symlinks, other-owner/world-readable files, wrong endpoints, missing read scope and broader settings/control scopes. Use a private directory and absolute paths on trusted CI hosts. Tokens never enter Kinmesh's operation journal. T3's grant must include `orchestration:read`; execution additionally requires `orchestration:operate`. Native permission mode is a separate ceiling: the adapter checks requested mode against discovered capability mode and provider mode support; T3 remains the final authority on launch/send/stop. Tool visibility never proves privilege.

Noninteractive execution never opens a browser or silently changes authorities. Expired/revoked grants fail authentication and require another explicit owner sign-in. There is no refresh-token emulation. Revoke native clients in T3 Sharing & access. Kinmesh account sessions and T3 OAuth grants are separate authorities; no HTTP endpoint exposes this adapter to arbitrary actor IDs or shared execution credentials.

## Contract and supported surface

`src/domain/execution.ts` owns `ExecutionBackend`, explicit project/scratch targets, operation intent, stable environment/thread/optional-run references, normalized observations and discriminated dispatch/wait/stop results. SDK/native types remain inside `src/adapters/t3`. This is a library plus smoke/auth CLIs, not a production team task dispatcher or unauthenticated execution API.

| Domain operation | External T3 tool / semantics                                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connect          | `t3_environment_read`, `orchestrator_capabilities`, SDK `tools/list`; pin primary identity and v0.1.5, resolve optional linked target separately                 |
| Launch           | `t3_thread_launch`, explicit project ID **or** `scratch: true`, advertised provider instance/driver/model, explicit permission mode, persisted `clientRequestId` |
| Read/history     | `t3_thread_read`, nested `thread`, `recentRuns`, `items`, `nextPosition`, `hasMore`; bounded message pages, explicit item truncation flags                       |
| Follow-up        | `t3_thread_send`, queue mode and persisted operation key; no silent steer/restart                                                                                |
| Wait             | `t3_thread_wait`, 1–20000 ms server wait; `timedOut` is a timeout, not successful completion; then authoritative read                                            |
| Stop             | `t3_thread_interrupt` for the requested run; acknowledgement alone is not terminal; authoritative read determines requested versus terminal                      |
| Reconcile        | persisted reference → read; otherwise replay only the same persisted command/key on the tested idempotent version, then read                                     |

Linked `environmentId` is passed as a routing target, **never** as a substitute for project/scratch selection. Primary and linked identities/version must match configuration. SDK reconnections revalidate primary identity/version before further tools. Reconnection does not retry mutations invisibly.

Read selects the requested run from `recentRuns`, rather than borrowing thread/latest status. `completed` maps to execution `succeeded`; interrupted/cancelled/rolled-back are terminal `stopped`; `waiting` remains nonterminal. Human acceptance is always `not-evaluated`. If a requested historical run lies outside the native 50-run window, return `uncertain`, not another run's success. Message pagination is exposed; text truncation is explicit. Token streaming and AG-UI projection are not implemented.

All invoked inputs/outputs are validated against installed advertised JSON schemas, with additional Kinmesh runtime invariants for target/model/version/identity and nested response projection. T3 v0.1.5 omits `outputSchema` on `t3_thread_organize`; the live cleanup-only archive call validates the documented dispatch `sequence` result instead. This cleanup helper is not an advertised core execution operation. The SDK also validates native tool outputs where supplied.

## Durable operations and recovery

Kinmesh's own `execution_operations` table records `(endpoint + environment scope, trusted actor, caller operationKey)`, input fingerprint, OAuth authority fingerprint, random stable native request ID, tool/payload, phase and provisional/known reference. The DB may contain sensitive prompts; protect and back it up as team data. The authority fingerprint is a hash, not a bearer token. Callers must supply an operation key from a stable business operation and derive the actor from their authenticated context; this CLI's local owner is trusted. Do not take either as permission from an unauthenticated request.

An immediate transaction persists intent **before** dispatch. Atomic compare/update claims the prepared row. A second caller sees in-flight/uncertain rather than creating another command. Input changes under the same key are conflicts. A genuinely different operation needs a new key; a retry does not. Keys are actor/endpoint/environment scoped and fingerprints additionally bind tool/target/payload/credential authority.

| Phase/outcome                                                                   | Safe next action                                                                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `prepared`                                                                      | Claim and dispatch persisted request ID                                                                |
| `dispatching`, crash, lost reply, timeout or in-flight cancellation             | Return discriminated `uncertain` with operation ID; explicitly reconcile, never invent a new retry key |
| Valid reply but read fails                                                      | Keep provisional reference; reconcile by authoritative read without a mutation replay                  |
| Valid reply + matching authoritative run/thread                                 | Atomically mark `known`; duplicate caller gets the stored reference                                    |
| Explicit native `capability_denied` or HTTP auth rejection before a valid reply | Persist rejection and fail; generic network/tool text is not denial evidence                           |
| Unsupported version/missing `clientRequestId`                                   | Fail before mutation; do not fall back to titles/PIDs/search heuristics                                |
| Reauthorization with a different authority fingerprint                          | Conflict, not a blind replay under another principal; owner must resolve existing intent/reference     |

An aborted client wait does **not** stop T3 work. Use an explicit authorized stop operation. Mutation cancellation after dispatch remains uncertain because the remote command may have committed. Per-fetch deadlines and SDK request timeouts bound transport requests; the native wait timeout remains a distinct domain result.

Reconciliation may safely replay exactly the old command/key if no reference was received. T3's native idempotency is the cross-system deduplication authority. No PID/lease/title marker or JSON-file lock stands in for it. Native permission/session/runtime-mode ceilings are never bypassed. T3 v0.1.5 refuses a send to an archived thread before replay (`thread_not_sendable`); unresolved sends remain uncertain until an owner deliberately unarchives that disposable thread and reconciles the **same** key. Do not switch to CLI or synthesize a new launch. Other native orchestration errors also fail closed as incompatible/uncertain rather than pretending to be permission evidence or completion.

## Verification and release policy

```sh
npm ci
npm run check          # all first-party types, type-aware lint, local tests, architecture
npm run format:check
npm run build          # emitted JS is ignored build output; stages committed migrations
npm audit --omit=dev
npm run test:contract  # explicitly MOCK/AUTH UNIT plus captured schemas; not a live pass
npm run test:live      # requires configured grants + reachable real T3; exits 1 when missing
npm run release:check  # candidate release is rejected unless authenticated live gate passes
```

Normal push/PR CI has **no execution credentials**, runs local/contract/build checks only, and does not label live integration green. A separate owner-dispatched workflow uses a dedicated `kinmesh-t3-acceptance` self-hosted runner with private configuration outside the checkout. Review code before running it; never attach that runner/authority to automatic untrusted PR events. The workflow is implemented, but no self-hosted GitHub live run is claimed here.

The live gate spends two model turns on disposable scratch threads: exact no-tools nonce completion, then a follow-up interrupted while active. It also loses an actual idle-launch reply, closes SDK/reopens the Kinmesh DB, replays the same native key and proves the original thread identity. A separate real read-only grant must return native `capability_denied` for a valid mutation. Cleanup archives its own threads; cleanup failure makes the gate fail. Output contains fixed pass/fail labels, never model text or credentials. Its private report is evidence only with that invocation's successful exit, not a reusable stale credential/CI pass.

| Browser OAuth consent UX                                                                                      | CLI implemented; actual human browser consent not witnessed by this headless run                                                             |
| T3 server process restart / upgrade                                                                           | Not performed on shared running server. Kinmesh DB reopen and MCP reconnect live; outages/version mismatch mocked. Unknown versions rejected |

Actual Kinmesh evidence is separate from historical Runner G0–G5. It does not establish full team task acceptance, multi-user authorization, browser E2E, or a restarted T3 service. Remaining acceptance: owner browser sign-in, dedicated live CI runner, safe disposable real T3 restart/version-upgrade probes, real project/linked-environment smoke if those deployment paths are used, and maintainer review. Keep the PR Draft. Adopt a new T3 version only after reviewing its public versioned schemas and running compatibility + authenticated live gates against that independently installed version; repair the adapter, never T3 internals.
