# Web workspace

Kinmesh serves a React workspace from the same Fastify origin as its authenticated HTTP API. React and Radix Tabs provide the component and accessible navigation foundation. The execution view uses the official `@ag-ui/core` 1.0 protocol and SDK validators through a small React headless snapshot consumer. It neither embeds T3 UI code nor connects the browser to a provider.

## Start and sign in

Use Node 24:

```sh
npm ci
npm run build
npm run setup
npm start
```

Open `http://127.0.0.1:3000/`. Sign in, or select **First owner setup** on a new installation. Setup requires the private setup secret generated by `npm run setup`; enter it only in the local trusted form, never in chat, URLs or a public terminal transcript. Username/password/team validation and the one-time claim are enforced by the existing setup endpoint. No anonymous caller can claim ownership. After setup, explicitly sign in. The masked CLI `npm run onboard` remains an alternative.

The browser keeps credentials out of local/session storage. Password/setup fields are masked; request credentials exist only in form/request memory and the server's protected session mechanism. Setup authorization uses the existing one-time secret, not a provider or agent token. Sign-out clears the encrypted HttpOnly, SameSite=Strict cookie and the displayed workspace. For remote use, deploy behind same-origin HTTPS with `KINMESH_ORIGIN` configured; see [security](security.md).

Build before source `npm start` to supply `web-dist/`. `npm run build` typechecks all first-party TypeScript/TSX, builds Vite assets, compiles server code and stages assets/migrations under `dist/`. The compiled server can run from `dist/src/server/main.js` with the same environment configuration. Without built assets, `/` returns 503 with a build instruction; `/api/*` and `/health` keep their API behavior. Only `/` and the built `/assets/` tree are served; no repository, credentials or generic SPA fallback is exposed.

For UI development, run `npm run web:watch` alongside the normal `npm start` after the initial build. Vite rebuilds public assets on source edits; refresh the browser after a completed build. All requests keep the same integrated origin, without relaxing CSRF checks or exposing a separate development listener.

## Collaboration flows

- Select a joined channel, create a channel, or rejoin one you left from **Rejoin a channel**, which lists them by name. Rejoin does not discover other channels, enroll a new user or restore removed membership. The first owner is enrolled in `general` automatically.
- Register an agent with a descriptive role, then explicitly add it to the selected channel. A profile does not configure T3, issue an execution credential or start work. Mention choices come from current active, joined agent memberships verified by the server.
- Read channel history, start/select topics, and post attributed plain-text messages with structured agent mentions. HTML is rendered as text. Channel and topic selection survive browser refresh in the URL. A configured Inbox may deliver mentions under its separate explicit deployment policy; the UI does not bypass that policy or call T3.
- Create a task with acceptance criteria, optional owner and distinct reviewer. Claim a proposed task as yourself, update your progress, request a review from a joined member, or explicitly hand off work. Responsibility is always evaluated by the server; a human cannot impersonate an agent to complete its transitions.
- The actual assigned reviewer may approve technical review or request changes. The designated human acceptor separately accepts an awaiting-human task or requests rework. No provider success or UI poll accepts anything. Each card binds its own immutable task ID, current expectedVersion, operation key and decision note. Activity expands persisted, attributed decision history and execution references.
- Inspect an agent's execution associations and recorded runtime reports. Waiting, failed, stopped and succeeded are distinct recorded observations with timestamps and human/agent provenance. An association is not proof that a native Run exists, nor is a reported success human task acceptance.

Agent credential issuance, profile preference editing and external Provider/OAuth configuration remain owner API/operator functions. Human invitations and arbitrary new team-member onboarding are not implemented. Current workspace administration uses the authenticated human owner policy; non-owner team membership does not imply owner privileges.

## Can an agent be woken?

The Team view, the sidebar, the agent panel and the `@` popover show whether an Inbox worker is currently connected for each agent (**Can be woken** / **Not connected · last seen …**). A registered profile without a running worker binding is shown as not connected before anyone mentions it. See [worker liveness](agent-inbox.md#worker-liveness-can-be-woken) for exactly what this does and does not prove.

## Setting up an agent

The agent panel shows a setup checklist from profile to a running worker: joined channel, runtime preferences (editable), a worker credential (issue, rotate, revoke; shown once, see [security](security.md#issuing-agent-credentials-in-the-browser)), T3 access (done on the worker machine), a generated `inbox.json` binding without secrets, and **Can be woken**, which only turns ready when a worker with that binding is running.

## What happened after you asked

Under each message that mentions an agent, and on a task the agent was handed, the workspace shows one line per agent describing its Inbox delivery in plain words: _will pick this up_, _isn't connected_, _is working on it_, _is waiting for an approval in T3_, _replied_ (a link to the reply, which shows what it answers), _is stuck_ (with the operator recovery command) or _never picked this up_. The machine state and reason are available as a tooltip.

`GET /api/workspace` includes these as `deliveries` for the visible messages and tasks of a channel the caller can read. Only identifiers, state, reason, timestamps and the reply message are exposed; claims, frozen launches, operation IDs, native references and counters stay in the worker. Blocked deliveries are still resumed only by an operator (see [Agent Inbox](agent-inbox.md)).

## AG-UI and refresh semantics

`GET /api/workspace` reconstructs the signed-in owner's team, joined channels, selected channel/topic message history, tasks and agent enrollment from Kinmesh-owned repositories. It accepts only bounded validated paging/filter parameters and never accepts an actor selector. Responses are `Cache-Control: no-store` and authorized through the existing server-derived principal.

`GET /api/agui/:teamId/:memberId` is a protected human-owner read. It validates current membership through the identity repository and returns **one official AG-UI 1.0 STATE_SNAPSHOT event**. Both construction and browser decoding use `@ag-ui/core/schemas`; the Kinmesh snapshot payload has its own strict Zod schema. It contains `source: kinmesh-persisted-reports`, snapshot-read time, the agent profile, execution references and attributed runtime observations. Persistent AgentId is never an AG-UI invocation ID, and ChannelId is never a T3 ThreadId.

These are HTTP snapshots, **not a run-event/token stream or fresh native T3 verification**. No RUN_STARTED/RUN_FINISHED, text deltas, tool activity or native approval controls are synthesized. The workspace polls every 15 seconds, refreshes after successful actions, and offers **Refresh now** in the command palette (⌘K / Ctrl+K) plus browser-online recovery. A healthy connection shows nothing; a status pill appears only for a refresh you asked for, a slow one, or a disconnect (with **Reconnect**). Sending depends only on the last refresh having succeeded for the channel on screen: a routine refresh never pauses typing or sending, while a failed one blocks every submission until a reconnect succeeds. Agent execution snapshots independently show a retry error if unavailable. Session expiry clears the workspace.

Responses show at most 100 channels/profiles, 50 messages/topics/tasks per page, and 20 execution associations with 100 reports each. Page controls use the existing bounded snapshot cursors; refresh begins reconstruction again and cannot turn a paged history into a token stream. Truncation is labeled. Full agent/execution history remains available through the authenticated APIs. The workspace projection bounds agent and execution reads in SQLite. Associations and reports use persisted append order, so tied wall-clock timestamps do not invent a newer observation.

## Optional private native observer

An owner can enable **Check in T3** with the paired server environment variables `KINMESH_T3_ENDPOINT` and `KINMESH_T3_AUTH_FILE`. Leave both absent for a workspace without native T3 access. Supplying only one, an empty value, or an invalid endpoint fails startup. The endpoint must be a canonical `https://host/mcp` URL (HTTP is allowed only on loopback), without userinfo, query or fragment. The auth file must be an existing, separately approved owner credential, outside the repository and web assets, owned by the server user with private mode `0600`. Do not paste its contents into the workspace, PR or logs. The credential must match the configured endpoint, contain `orchestration:read`, and identify the same environment as the persisted execution reference. This feature does not acquire, renew, save or expose OAuth tokens. Existing credentials with `orchestration:operate` remain usable, but this observer never invokes operating tools.

`GET /api/teams/:teamId/agents/:agentId/executions/:executionId/native` requires a current Kinmesh human owner session. Agent bearer credentials are denied. The server retrieves the exact immutable association in that team and agent before reading any private credential. Neither request query parameters nor browser input can choose the endpoint, credential, environment or thread. The official external MCP SDK checks the environment/version and validates the discovered read schemas, then calls only `t3_environment_read` and `t3_thread_read`, under an eight-second total deadline. The observer rejects redirects and does not perform OAuth discovery or consent. It rechecks owner access after the remote read and never saves the observation as an AG-UI report.

Each run card keeps what the agent **last reported** (AG-UI state snapshots) separate from what **T3 confirms** on an explicit check, including the exact native Run status. Thread/run IDs and protocol details sit under **Technical details**. Checks are explicit, without native polling or automatic retries. A Run outside the latest 50 Runs is `unobserved`, nonterminal, with unknown provider/model; thread status cannot overwrite it. Pending request counts are explicitly thread-scoped and are not attributed to the selected Run. `waiting` remains nonterminal; `interrupted`, `cancelled` and `rolled_back` retain their exact stopped-state spelling. A thread-only association labels its thread status instead of claiming a Run observation. A native result is a timestamped read, not a continuing live feed or task acceptance.

**Open in T3** appears only when T3 actually supplied `thread.link` and the server validated its exact configured endpoint origin and decoded environment/thread path. Missing links, custom `t3-thread://` links, foreign origins, userinfo, query/fragment, invalid encoding and mismatched IDs produce no link. Kinmesh never constructs a URL from IDs. The workspace snapshot exposes only the approved native origin (`nativeT3Origin`, or null), never an OAuth endpoint path or credential. The browser strictly decodes the DTO, binds it to the requested reference and that separately configured origin, checks browser URL/path safety, and opens accepted links with `target="_blank" rel="noopener noreferrer"`; origin authorization is enforced on the server against private configuration.

Missing configuration, unsafe/missing credentials, issuer/environment mismatch, native authentication/permission/schema failures and network outages return the same generic HTTP 503. They clear the displayed native result and link without signing out the Kinmesh owner. Actual Kinmesh 401/403 denials clear both native results and protected execution snapshots. No native approval, send, launch, interrupt or model execution control is available here.

Native acceptance requires an authenticated observer and a returned original-T3 browser link in a real, separately approved T3 environment. Code-only tests and local deterministic mocks provide no live native evidence. See the [v0.1 acceptance record](acceptance/v01-workflow-2026-10-31.md) for actual observations and their limits. The T3 OAuth grant used by Kinmesh does not establish a T3 browser session; a desktop-managed T3 browser may separately require pairing before it displays the thread.

## Errors and idempotency

Browser API requests use same-origin credentials and server Origin checks. Static/API responses carry restrictive CSP, no-referrer and nosniff headers. React text rendering escapes team content; no raw HTML renderer is used. No T3 OAuth file, provider login, Agent grant or private prompt is sent to the browser.

Mutation forms create supported DTOs with a new operationKey for a new logical action; task commands carry the rendered expectedVersion. HTTP 403/409/429 and authentication errors are shown explicitly, without optimistic success. A network-ambiguous mutation retains the exact submitted request/key in component memory, disables editing and offers an explicit **Retry same action**. It is not automatically resent. Reloading discards unsent/retry form memory; inspect durable state before creating another logical action. Unkeyed profile registration is protected by the existing team-name uniqueness rule; a lost-response retry can return 409, requiring inspection. Setup/login are not domain idempotency operations.

## Browser checks

```sh
npm ci
npx playwright install --with-deps chromium
npm run build
npm run test:browser
```

Playwright launches real Chromium against disposable Fastify subprocesses and SQLite databases, with generated local secrets and a minimal environment excluding Inbox/T3 credentials. Tests fail if browser installation/launch/interaction fails; there is no HTTP-only fallback. CI installs Chromium explicitly. Browser tests exercise desktop/mobile setup/login, channels, enrollment, topics, persistent messages/mentions, refresh/offline reconnect, independent task decisions, owner acceptance/rework, protected AG-UI snapshots, schema-valid persisted execution reports and security denials. Agent actions in responsibility tests use an independent local scoped HTTP client; execution-reference fixtures are explicitly synthetic and never native model evidence. Browser traces/videos are off to keep authentication material out of artifacts.

The ordinary `npm run check`, `npm run format:check`, `npm run build` and production audit remain required. Browser tests use no T3 installation, OAuth or paid models. Real native status/link acceptance and automatic worker/provider acceptance still require their separate authorized integration gates. Native observer HTTP/SDK tests use an explicitly labeled local protocol fixture; browser mock observations only exercise rendering, strict decoding and stale-result removal. The real unconfigured browser path checks the production 503 fallback and preserves its owner session.
